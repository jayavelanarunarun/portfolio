Initiative 01 / 03

On-Demand Refresh

User problem

Users had to wait for scheduled discovery cycles before infrastructure changes appeared in Inventory — blocking decisions, configuration validation, and recovery from stale data.

On-Demand Refresh

Enable on-demand refresh of supported discovery resource types directly from Inventory — giving operational teams immediate control over data accuracy and freshness without waiting for scheduled cycles.

How I led discovery

Before any UX ideation, I drove a structured discovery phase — challenging assumptions, mapping system boundaries, and aligning architecture before design work began.

PhaseOutcomeWhat I did
FramingValidated the operational need for on-demand inventory refreshChallenged the core assumption: “Why would a user manually refresh if automatic discovery exists?”
RequirementsDefined refresh scope across resources and resource typesFacilitated grooming sessions to surface edge cases — failed refreshes, stale data, scope variants
ArchitectureDefined the architectural blueprint for refresh orchestration, supportability, and operational traceabilityLed multiple architecture alignment sessions before any UX ideation
JTBDSynthesised multiple use cases, edge cases, and stakeholder perspectives into one guiding JTBDSynthesised requirements into a single clear job-to-be-done statement

Defined JTBD

“When I create, modify, or delete resources at the source provider, I want to refresh affected inventory records on demand so Inventory reflects the latest resource state immediately and supports accurate decisions.”

UX challenges I navigated

Each challenge required cross-functional decision-making, not just design resolution.

01

Discovery vs. Inventory ownership — a system boundary decision

Uncovered through stakeholder workshops that refresh was not a single-location action. I helped define a multi-level refresh strategy, exposing resource refresh in Inventory 3.0 and provider-, connection-, and registration-based refresh in Discovery Management, reducing ambiguity around ownership, navigation, and implementation scope.

02

Designing for multiple refresh scopes without overwhelming users

The system needed single resource, bulk selected, provider-level, and registration-level refresh — each with different triggers and contexts. I designed a scope model that surfaced the right action at the right level without burdening the default experience.

03

Communicating long-running async jobs

Refresh was asynchronous. I identified that users needed confidence a job had started, was running, had completed, or had failed — without leaving their current view. This shaped the entire status communication pattern.

04

Identifying missing visibility — the “Refreshed At” insight

Discovered that users might not distinguish between scheduled and manually triggered discovery. I introduced a “Refreshed At” indicator with distinct iconography for each refresh type, providing greater clarity, traceability, and trust in inventory data freshness.

Key design decisions

→
Async status communication — progress, completion, and failure states designed to be visible without requiring navigation away from the table.
→
“Refreshed At” column — designed a new inventory signal that differentiated scheduled and on-demand refreshes, giving users greater visibility into data recency and refresh origin.
→
Batch-first approach — aligned refresh to existing table-selection patterns so users could initiate single or bulk refresh without a separate flow.
→
Contextual action placement — refresh actions surfaced within existing inventory workflows, not as a separate feature destination.

Initiative 02 / 03

Column Settings Enhancements

User problem

Users working with data-heavy inventory tables found it difficult to locate and configure columns across a growing set of attributes. The existing experience offered limited visibility into selected columns, their order, pinned state, and default configuration, making table customisation time-consuming and difficult to manage.

Data Table

Redesigned the table-column configuration experience to help users find, select, organise, pin, and restore columns while working with large infrastructure datasets.

How I led this initiative

I examined the end-to-end column-management workflow, identified gaps across column discovery, selection, ordering, and reset behaviour, and translated the findings into a more structured configuration experience. I iteratively explored the side-panel interaction, clarified control behaviour, and aligned the experience with existing table patterns.

System coherence

Designed the experience as an extension of the existing table-settings pattern, maintaining consistency between the configuration panel and the resulting table view.

Behaviour definition

Defined how search, select all, individual selection, ordering, pinning, and restore-default actions should behave across different user states.

Interaction audit

Mapped the existing column-management flow and identified friction in finding columns, understanding selection states, and managing a large number of attributes.

Key design decisions

→
Clear selection management — defined select-all, individual selection, and mixed-selection states to provide accurate feedback as users configured visible columns.
→
Pinning and default recovery — incorporated persistent column positioning and a restore-default option so users could customise the table without losing a reliable way back to its original configuration.
→
Searchable column list — introduced search within the settings panel so users could quickly locate specific attributes without scanning the complete list.
→
Position-based ordering — enabled users to understand and control the order in which selected columns appear in the table.

Initiative 03 / 03

Global Inventory Search — Metadata Summary View

User problem

Global Inventory Search surfaced relevant resources but not the bigger picture. Large result sets made it difficult to understand where matches occurred, how they were distributed across the global inventory, and where further investigation should begin.

Metadata summary view

Redesigned Global Inventory Search to transform attribute-based search results into a metadata-first summary, helping authorised users understand where matching resources were located and how those matches were distributed across data planes, regions, customer accounts, and tenants before examining individual records.

How I led discovery

I partnered with a cross-functional group to understand the full range of search behaviours — from executive threat investigation to operational asset lookup — and synthesised a design direction that served both without duplicating the experience.

UX challenges I navigated

Each challenge required me to facilitate stakeholder alignment, not just make a design decision unilaterally.

01

Reframing global search from retrieval to insight

Global Inventory Search surfaced matching resources, but not their broader context. I introduced a metadata-first model that helped users understand the scale and distribution of search results across the inventory before investigating individual records.

02

Determining the right metadata dimensions

A high-level count alone was not sufficient. I worked with stakeholders to define which metadata attributes helped users make decisions, eventually shaping the summary around customer, tenant, location, device counts, resource classification, provider information, and product attributes while keeping the table scannable and comparison-friendly.

03

Defining meaningful metadata aggregation

A simple count of matching resources provided limited insight. I worked with stakeholders to define a metadata model that surfaced distribution and ownership across data planes, regions, customer accounts, tenants, and resource categories, enabling users to compare result groups before drilling into individual records.

04

Maintaining one search experience instead of two

There was a risk of turning Metadata Summary and Detailed View into separate experiences. I advocated for a unified interaction model where users could switch between summary and detail without losing search context, filters, selected accounts, or navigation state, creating a more coherent search workflow.

Key design decisions

→
Toggle-based view switching — a lightweight mechanism to move between summary and detail without navigating away or losing context.
→
Hierarchical result organisation — search results are structured by Data Plane and Region, helping users progressively narrow their focus from global scope to specific customer environments.
→
Metadata-first entry point — users land on Metadata Summary; Detailed Records are one step away when investigation begins.
→
Count-driven comparison model — metadata summaries prioritise resource counts and ownership dimensions, enabling users to assess impact without inspecting individual assets.

Workflow · Inventory · Operations

Inventory 3.0

An on-demand discovery experience that helps operations teams refresh resource information when they need it, without waiting for the next scheduled cycle.

Role

Senior Lead UX Designer

Focus

On-demand discovery · Resource inventory

Partners

Product, engineering and operations teams

Design scope

Workflow design · Selection · Status feedback

01Challenge

Let teams refresh inventory on demand

Users needed a clear way to select resources and start discovery without waiting for a scheduled run. The workflow also needed to make supported categories, current progress, partial success and failure states easy to understand.

The design connects the inventory table, resource selection and run feedback so users can stay oriented from initiation through completion.

Design prompt

How might we let operations teams refresh the resources they need, understand what will run, and trust the result?
